# 转换算子索引

以下算子是本文件示例的通用抽象：

| 算子 | 目标 |
|---|---|
| `NEGATION → OWNERSHIP` | 将“X 不负责 Y”转换为 Y 的明确职责归属 |
| `WARNING → RULE` | 将提醒转换为正式规则 |
| `CLAIM → MECHANISM` | 将空泛结论转换为实现机制 |
| `CLAIM → ACCEPTANCE_CRITERIA` | 将“完善/可靠”等自评转换为验收条件 |
| `PROCESS → FACT` | 删除审计、讨论、修改过程，仅保留最终事实 |
| `TEMPORARY → SCOPE` | 将“暂时/第一版”转换为明确阶段边界 |
| `DEFENSE → DEFINITION` | 将“不是/不等于/不意味着”转换为正向定义 |
| `FUTURE_PROMISE → ROADMAP | DELETE` | 将未来承诺放入明确路线图，否则删除 |
| `VAGUE → CONDITION` | 将模糊措辞转换为条件、触发器或指标 |

# 中文技术文档转换示例

本文件提供常见 Working Draft → Final Document 转换模式。学习语义转换，不机械套用句式。

## 1. 否定职责 → 明确所有者

Before:
> Query Engine 不负责权限判断。

After:
> Authorization Service 负责权限判断；完成授权的请求进入 Query Engine 执行。

## 2. 禁止行为 → 正向规则

Before:
> 这里不要直接访问数据库。

After:
> 数据库访问统一通过 Repository 层完成。

## 3. “不是完整实现” → 明确交付范围

Before:
> Phase 0 不是完整的生产版本。

After:
> Phase 0 交付配置加载、查询执行链路和基础错误模型；生产可观测性与高可用能力在 Phase 1 完成。

## 4. “并不意味着” → 直接陈述约束

Before:
> Trusted 并不意味着可以绕过安全检查。

After:
> TrustedQuery 执行前统一经过权限校验、SQL 验证和执行策略检查。

## 5. “需要注意” → 删除包装

Before:
> 需要注意的是，所有写操作必须在事务中执行。

After:
> 所有写操作必须在事务中执行。

## 6. 审计过程 → 最终事实

Before:
> 经过本轮审计，我们发现原来的连接池配置存在问题，因此已经调整为最大 20 个连接。

After:
> 数据库连接池最大连接数为 20。

若配置原因具有长期价值，可补充稳定依据，而不是审计过程。

## 7. 临时实现 → 阶段交付

Before:
> 第一版先只做 Oracle，其他数据库以后再说。

After:
> Phase 1 支持 Oracle 19c。Phase 2 通过统一 Dialect 接口扩展数据库适配能力。

## 8. 无主语要求 → 责任归属

Before:
> 需要记录所有查询的审计日志。

After:
> Audit Service 记录查询发起人、时间、数据源、查询标识、执行结果和耗时。

## 9. 空泛质量要求 → 可验证机制

Before:
> 系统需要保证高可用和稳定性。

After:
> API 实例保持无状态并支持水平扩展；数据库连接失败采用有界重试；健康检查覆盖进程、数据库连接和关键依赖。

## 10. “确保” → 机制 + 验证

Before:
> 确保重复请求不会产生重复数据。

After:
> 写接口使用业务幂等键建立唯一约束；重复请求返回首次成功写入对应的结果。

## 11. 防止误解 → 准确定义

Before:
> 不要把 Repository 理解成业务层，它只是负责数据库操作。

After:
> Repository 封装持久化操作；领域规则由 Application Service 和 Domain 层实现。

## 12. 多句防御 → 单一权威定义

Before:
> Scheduler 不执行任务。它不是 Worker。这里不要理解为 Scheduler 会直接运行任务。真正执行任务的是 Worker。

After:
> Scheduler 计算任务触发时间并向队列提交执行请求；Worker 消费请求并执行任务。

## 13. “为了避免” → 最终架构

Before:
> 为了避免各模块自己处理数据库连接，我们增加了统一的数据访问层。

After:
> 数据库连接和持久化操作由统一的数据访问层管理。

若集中管理的原因属于关键架构决策，可在 ADR 中记录。

## 14. 作者思考 → 设计事实

Before:
> 我们认为这里使用异步方式会比较合适。

After:
> 报表生成采用异步任务执行，API 在创建任务后返回任务 ID，客户端通过任务状态接口查询结果。

## 15. “原则上” → 明确条件

Before:
> 原则上失败任务可以重试。

After:
> 网络超时和临时依赖故障最多重试 3 次；参数校验失败和业务规则错误不重试。

## 16. “尽量” → 可执行规则

Before:
> 尽量避免在接口中返回内部错误信息。

After:
> 外部 API 返回标准错误码和用户可读消息；堆栈、SQL 和内部异常信息仅写入服务端日志。

## 17. 自我评价 → 验收标准

Before:
> 该设计具有良好的可维护性。

After:
> 数据访问、业务规则和协议适配分别位于 Repository、Application Service 和 API 层；模块依赖方向通过架构测试验证。

After（已进入路线图）:
> Phase 2 增加 PostgreSQL 适配器，并复用统一 Query Dialect 接口。

After（尚未决策）:

## 19. 重复强调 → 一次定义

After:

## 26. 转换判断顺序

遇到疑似坏味道时按以下顺序处理：

1. 删除后是否损失必要信息？否 → 删除。
2. 是否包含真实安全、数据、API、运维或合规约束？是 → 保留并提高精确度。
3. 是否在表达职责边界？是 → 找到责任主体，改为所有权描述。
4. 是否在表达阶段范围？是 → 改为交付物、阶段和验收条件。
5. 是否包含长期有效的设计依据？是 → 提取稳定依据。
6. 其余情况 → 提取最终事实并直接陈述。
