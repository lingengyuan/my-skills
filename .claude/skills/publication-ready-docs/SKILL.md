# Publication Ready Docs

工程文档让读者能独立理解、实施、运行和验证。先查证事实，再确定本次必要内容，先删后改，最后核对语义。

## 内容范围

- **详细设计 / 技术方案**：目标、规则、改动对象、职责、接口契约、状态流转、关键代码和配置。
- **运行手册**：前置条件、操作步骤、回滚和恢复。
- **测试与审计**：验证场景、预期结果、实测结果；审计、复盘和 ADR 保留必要权衡。

按文档类型和任务取舍章节，按真实主题合并零碎小节，标题层级统一。部署、测试或审查证据按需写入。

## 工作流程

1. **查证来源**：核对源码、规范、表结构、配置与既有详设。简述复用机制与本次差异。需要定位时标注模块、文件、类、函数或配置项。
2. **确定内容**：列出读者需要的事实、规则、改动对象、关键代码和配置。先用可用工具查源码、规范、配置和已有查询结果；需要用户协助时，在会话给出具体查询项或 SQL，取得结果后写入正文。影响方案成立的外部业务条件保留，并在会话确认。
3. **区分状态**：分别写清现有行为、拟设计方案和已实施结果。
4. **先删再润色**：删除后读者仍能完成任务的内容直接删去。保留内容简写为规则和条件。清理过程记录、自我评价、空泛承诺、重复定义、模板空章节和无新增信息的提醒。
5. **去重**：一个事实只定义一次。字段位数、枚举和约束写在表格时，正文只写表格未覆盖的类型和解析规则。同步检查正文、表格单元格、括注和代码注释。仅清理文字和注释时，代码执行语句保持原样；方案调整时，同步修改代码和契约。
6. **核对并同步**：核对语义、边界、职责、数值和未决条件。仅审查时交付审查结果；获得授权后，基于最新版本局部修改正文、表格、代码和前提条件，改后回读，沿用项目约定的模板，保留既有图表资源。交付前按参考复核。

## 写作规则

- 短句、主动语态、一句一个要点。术语首次出现时定义，全篇用同一叫法。条件写在动作前。命令、路径、表名和字段名用代码格式。
- 规则写清主体、条件、动作和结果。必要边界用正面具体指令表达，例如“只更新 `A` 表的 `B` 字段”。
- 字段禁填、长度、枚举含义、事务边界、失败后果、兼容性和数据写入范围保留一次。
- 引用外部规范时保留其条件、建议强度和例外。规范已有定义时直接引用或链接。项目补充只写已确认的差异和新增约定。其余比较、提醒和复述删去。
- 直接陈述规则和条件，删除包装语、防御性对照和过强语气。
