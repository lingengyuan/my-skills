# Publication Ready Docs

用于生成和整理可直接提交、发布、评审和长期维护的正式技术文档。

核心目标：最终文档只保留读者需要知道的内容，不保留生成这些内容的工作过程。

## 1. 发布边界

工作过程可以包含分析、推理、探索、方案比较、质疑、Review、Audit、修正和验证；最终文档保留事实、职责、架构、接口、流程、约束、决策、交付范围和验收标准。

审计结论可以进入最终文档，审计过程本身不进入最终文档。

## 2. 描述“是什么”

优先直接定义系统、组件、流程和规则，不通过大量排除项定义概念。

不推荐：
> Query Engine 不负责权限判断。

推荐：
> Authorization Service 负责权限判断，完成授权的请求进入 Query Engine 执行。

## 3. 描述最终状态

以设计已经确定、文档已经定稿的视角写作，不记录作者如何得到结论。

不推荐：
> 经过分析，我们最终决定使用 Repository 模式。

推荐：
> 数据访问采用 Repository 模式，以统一持久化边界并隔离数据库实现细节。

## 4. 用职责代替排除

遇到“X 不负责 Y”时，确定谁负责 Y，并直接描述职责归属。

不推荐：
> API Handler 不应该包含业务逻辑。

推荐：
> API Handler 负责协议适配和请求校验；业务逻辑由 Application Service 负责。

## 5. 用规则代替提醒

不推荐：
> 这里需要注意，不要直接访问数据库。

推荐：
> 数据库访问统一通过 Repository 层完成。

正式文档定义规则，而不是提醒读者“小心”。

## 6. 先删后改

发现防御性解释、中间过程、审计语言、元话语、预防误解、重复解释或无信息量提醒时，先执行 Delete Before Rewrite（先删后改）。

判断：删除这句话以后，是否会影响读者正确理解、实施、运行或验证系统？

- 不影响：直接删除。
- 有影响：提取事实、职责、约束、决策、接口、流程或验收条件，再重新表达。

示例：
> 需要特别注意的是，这里的 Trusted 并不意味着可以绕过安全检查。

改为：
> TrustedQuery 执行前统一经过权限校验、SQL 验证和执行策略检查。

## 7. 区分必要否定与防御性否定

本 Skill 不禁止否定句。判断标准是这句话是否表达真实规则。

以下表达应保留：
- Token 不得以明文形式持久化。
- `completed` 状态不得回退到 `pending`。
- 不同业务事务不得复用同一个 `transaction_id`。
- 两个数据库节点不得同时执行重启操作。
- 审计记录写入后不得修改。

需要清理的是以解释、防御或预防误解为主要目的的否定表达。

## 8. 清理工作过程

除非文档本身就是审计报告、复盘报告或 ADR，否则默认删除“经过分析”“经过审查”“我们发现”“上一版存在”“审计过程中发现”“为了避免误解”“需要注意”“经过讨论决定”等过程语言。

最终文档描述结论，而不是结论产生的过程。

## 9. 删除元话语

删除只是在介绍、强调或包装下一句话的表达，例如“需要注意的是”“值得一提的是”“需要强调的是”“显然”“严格来说”“简单来说”“换句话说”“如前所述”“可以看到”“我们可以发现”。

如果删除开头后语义不变，直接删除。

## 10. 控制预防误解式写作

不要围绕假想的错误读者反复写“X 不是 Y”“这并不意味着 Z”“不要把 X 理解成 A”。

优先通过 Purpose、Responsibilities、Inputs、Outputs、Dependencies、Lifecycle、Constraints 准确定义 X。

## 11. 保留有长期价值的设计依据

架构决策、性能权衡、安全决策、兼容性要求、不可逆设计、非显然约束和运维影响具有长期价值时应保留。记录稳定的设计依据，而不是讨论过程。复杂决策历史进入 ADR。

## 12. 每句话都必须有存在价值

正式技术文档中的句子原则上至少提供一种信息：事实、职责、关系、接口、行为、约束、决策、依据、操作或验收标准。

主要承担过渡、强调、重复、安抚、防御、预防误解、描述作者思考或审计过程作用的句子，删除后不损失有效信息则删除。

## 13. 根据文档类型调整规则

- 架构设计/详细设计：系统结构、模块职责、组件边界、数据流、调用关系、接口、设计决策、非功能要求。详设排除（默认口径，用户明确要求合并交付时按用户口径执行）：实施步骤、部署顺序、联调与验证计划（属实施计划）；数据与脚本维护说明（归入对应交付物的注释）；内容已被后文章节覆盖的总结句。
- 测试用例/测试报告：用例定义、步骤、输入/消息样例、预期结果、执行记录与证据链接；测试工具与方法学细节（由什么程序/框架生成、采用了何种裁剪）不属于交付内容，只陈述验证场景与结论。
- 实施计划：目标、交付物、任务、依赖、实施顺序、完成条件、验证方式。
- README：项目用途、安装、配置、使用、示例、运行要求、常见操作。
- API 文档：契约、参数、返回值、错误、不变量、示例。
- Runbook：允许命令式和禁止式表达，因为它们属于操作规则。
- ADR：保留背景、备选方案、决策、取舍和后果。
- Audit/Review：允许否定、比较和批判性语言，因为分析本身就是交付物。

## 14. 审计与发布分离

任务同时包含开发、审查、严格审计和更新文档时，拆成两个阶段：

阶段 A：内部审查——检查、质疑、对比、找问题、验证、修正。

阶段 B：正式发布——提取最终事实、确认职责、确认边界、确认规则、删除工作过程、防御性解释和重复信息。

阶段 A 的结论影响阶段 B；阶段 A 的语言不得直接复制到阶段 B。

## 15. Publication Pass

文档完成后执行独立的发布稿清理，不继续扩写。

1. 按 §6（先删后改）、§8（工作过程）、§9（元话语）、§10（预防误解式写作）、§12（句句有存在价值）逐节扫描，并应用文末转换算子；需要更多示例时读取 `references/anti-patterns.md` 与 `references/transformations.md`。
2. 同一事实只保留一个权威定义。删除总结性或重复段落时，先提取其中未在权威章节出现的约束与决策，合并到该事实的权威定义；只删表述，不删约束。
3. 文档涉及复用的既有逻辑、函数或配置参数时，标注来源（沿用的界面、SQL 或函数名），区分新设计与既有行为。
4. 文档定义了状态机或流程时，每个状态写明进入条件（触发场景）与转出行为。
5. 发布稿包含占位内容（TODO、待定值、示例 URL）时，消除或显式标注为待确认项及其确认责任人。
6. 删除后不影响理解、实施、运行或验证的内容直接删除。
7. 文档中的示例代码遵循目标代码库的既有风格：注释的位置与粒度、缩进、命名，与同库同类文件一致；不为文档另造注释风格。
8. 文档引用的交付物（报告、用例、日志、脚本）以上线链接或附件形式挂载在文档内；只写文件名的引用视为悬空引用。
9. 执行/结果类文档不留"（执行时填写）"类待填空位——完成后回填实际结果与证据；工具与方法学细节不进交付文档，只陈述验证场景与结论。

详细坏味道见 `references/anti-patterns.md`，常见转换方式见 `references/transformations.md`。

## 16. 最终质量门禁

- [ ] 文档像正式项目资料，而不是 AI 对话记录。
- [ ] 正文直接描述系统或目标状态。
- [ ] 不包含内部推理、无必要审计过程和中间版本说明。
- [ ] 不通过大量“不是”定义概念。
- [ ] 不围绕假想误解反复解释。
- [ ] 防御性语言已经删除或转换。
- [ ] 影响面安抚句（“仅涉及 X，其他不变”“无新增风险”“与现状一致”）已删除；范围由改动位置和交付物表达。
- [ ] 必要的安全、数据、API、运维约束得到保留。
- [ ] 每项重要职责都有明确所有者。
- [ ] 范围通过交付物和边界表达。
- [ ] 架构通过组件、关系和流程表达。
- [ ] 规则直接表达为规则。
- [ ] 重复解释已经合并。
- [ ] 术语前后一致。
- [ ] 改写、搬运或精简含否定词的约束句后，已逐条核对否定词保留、语义方向未反转。
- [ ] 状态机、响应矩阵覆盖全部合法状态与响应取值，且每个状态有进入条件。
- [ ] 每个段落都提供新的有效信息。
- [ ] 每句话都有存在价值。
- [ ] 无"已移除 / 已裁剪 / 已修复"类编辑过程叙述；直接陈述当前状态。
- [ ] 无依赖作者执行历史的指代（"此前联调""之前讨论的"），相关内容已改为自足描述。
- [ ] 文档内引用的交付物均可点击或以附件挂载。
- [ ] 文档脱离 Prompt、Agent、Review 和 Audit 上下文后仍能独立成立。

## 17. 最终阅读测试

以一个刚加入项目、没有参与前期讨论的工程师视角阅读文档。

读者应该能够回答：这是什么、为什么存在、如何工作、谁负责什么、组件关系是什么、边界在哪里、有哪些规则、需要实现或运行什么、如何判断完成。

读者不需要知道 AI 思考过什么、Prompt 要求过什么、Review 质疑过什么、Audit 发现过什么、初稿写错过什么、作者担心读者误解什么或文档经历过几轮修改。

读者也没有执行者的会话历史：凡指代"此前联调""之前讨论""上一轮测试"的内容，必须改为自足描述（对象是什么、从哪里获取），否则删除。

评审中读者提出的每个澄清问题（“这是什么意思”“什么情况下会出现”）都对应一处可改进的表述：优先完善文档，而不是只做口头解释。

最终文档本身就是交付物。生成它的过程不是。

# 执行协议

每次处理正式技术文档时，按以下顺序执行：

1. 识别文档类型：架构/详设/计划/README/API/Runbook/ADR/Audit。
2. 完成内容工作：先保证技术事实、结构、范围和决策正确。
3. 执行 Publication Pass（§15）：应用先删后改与转换算子。
4. 执行语义保持检查（见“语义保持与优先级”）与最终质量门禁（§16）。
5. 只将最终可交付内容写入正式文档；审计过程保留在对应审计产物中。
6. 发布稿相对源文档存在裁剪或修正，且源文档仍是后续维护基础、用户交付范围包含源文档同步时，将裁剪与修正决定回写源文档；否则在发布稿或源文档中标注差异。同一文档存在两个版本时，只有一个是权威事实源。
7. 对已发布文档的每次增量修改，修改部分同样执行小范围 Publication Pass 与质量门禁；发布不是免检状态。
8. 技术口径变更时，同步修改覆盖四层：正文叙述、表格、代码块（含 DDL）、假设/前提清单——并对旧口径关键词做全文残留校验；常见漏点是代码块、DDL 与假设清单。

# 语义保持与优先级

Publication Pass 属于**语义保持型重构**。文风优化不得改变技术事实、接口契约、安全约束、范围边界、验收标准和已批准决策。

优先级固定为：

`正确性 > 完整性 > 可实施性 > 信息密度 > 表达质量`

当表达优化与前四项发生冲突时，保留原有有效信息并改进其表达，不得为了消除否定句或缩短篇幅而删除真实约束。

# 转换算子

优先按语义应用以下转换，而不是机械替换词语：

- `NEGATION → OWNERSHIP`：否定职责 → 明确职责所有者。
- `WARNING → RULE`：提醒/警告 → 可执行规则。
- `CLAIM → MECHANISM`：空泛主张 → 实现机制。
- `CLAIM → ACCEPTANCE_CRITERIA`：自我评价 → 可验证验收标准。
- `PROCESS → FACT`：工作/审计过程 → 最终事实。
- `TEMPORARY → SCOPE`：临时状态 → 明确阶段范围。
- `DEFENSE → DEFINITION`：防御性解释 → 准确定义。
- `FUTURE_PROMISE → ROADMAP | DELETE`：未来承诺 → 明确路线图，否则删除。
- `VAGUE → CONDITION`：模糊要求 → 明确条件、触发器或指标。

# 反过度优化

正式文档不是信息清单，Publication Pass 的目标也不是最短文本。

保留对理解和实施有价值的背景、设计依据、上下文、示例、流程解释和组件关系。删除的是工作过程、重复、防御性解释和无信息量语言。

最终文档应同时满足：

- 信息完整；
- 结构清晰；
- 自然可读；
- 可独立理解；
- 可直接交付。

如果清理后的文档只剩孤立规则和条目，应恢复必要上下文，而不是继续压缩。
