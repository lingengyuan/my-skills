# Document Templates

> **去 AI 味核心原则**：
> 1. **严禁强行升华**：不要把普通的工程事实包装为“心智模型”或“哲学框架”。如实记录机制与代码。
> 2. **严禁虚构伪洞见**：没有反直觉发现就不写该节，禁止用套路化的推论链（“洞见→所以→因此可以”）制造虚泛深度。
> 3. **严禁无病呻吟的连接**：知识库中无直接强关联文件时，直接删除“关联文件”小节，不得硬凑。
> 4. **按需裁剪**：以下模板中的章节除核心事实外均为可选，根据材料实际价值按需选用，宁缺毋滥。

---

## 1. 技术精读与架构分析（`analysis/{topic}.md`）

适用于深入剖析系统设计、开源框架或复杂工程实现的分析笔记。

```markdown
# {标题} 精读

**来源**: [{标题}]({url})
**日期**: YYYY-MM-DD
**标签**: tag1, tag2

---

## 解决的问题与结论

> {1~2 句话直接阐述：该技术解决了什么痛点？核心结论是什么？开门见山，不写铺垫。}

## 核心工作机制

{解析系统工作原理，注重因果关系和技术决策，而非流水账。}
- **关键设计决策**：{为什么这样设计，而不是别的方式}
- **最小执行链路**：{核心调用链路或状态流转}

```language
// 关键代码或最小配置示例
```

## 适用边界与权衡

- **适合场景**：{什么时候应该用}
- **不适合场景 / 局限**：{什么时候不该用，哪些场景会失效}
- **已知陷阱 / 失败模式**：{真实环境中的踩坑点或性能瓶颈}

## 关键可复用资产（可选）

- 可直接复用的函数、配置模板或 CLI 片段。

## 反直觉发现（可选，仅当原文明确具备时保留）

- {原文中真正打破常规认知的技术细节或实测数据，绝不无中生有。}
```

## 2. 灵感与技术验证笔记（`ideas/{topic}.md`）

适用于记录新工具带来的灵感、衍生项目想法或工程探索。

```markdown
# {标题}

**来源**: {原始 URL 或讨论}
**日期**: YYYY-MM-DD
**状态**: 💡灵感 / 🔄 验证中 / ✅ 已实现

---

## 灵感概述

> {一句话说明：这个灵感解决什么具体问题，核心切入点是什么}

- **触发痛点**：{当前哪一步操作过于繁琐或缺失}
- **核心切入方案**：{用什么现成工具/模型/API 快速突破}

## 最小验证方案 (Spike)

能在 1 天内跑通的最小闭环：
1. 步骤一：{安装依赖或拉取模型}
2. 步骤二：{核心胶水脚本}
3. 验证标准：{怎么确认这个想法成立}

## 潜在卡点与边界

- {已知的技术阻碍或成本限制}
```
