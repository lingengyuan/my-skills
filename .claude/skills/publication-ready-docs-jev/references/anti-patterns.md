# 常见坏味道

先按主文档规则判断删除，再决定是否改写。没有新增信息的提醒整句删除。按信息价值和项目必要性判断。

| 表达 | 处理 |
|---|---|
| “不负责”“不涉及”“其他不变”等范围排除或安抚 | 提供职责、兼容性或影响事实时保留并写具体；只安抚时删除 |
| “需要注意的是”“为了避免误解”“值得强调” | 删除包装，保留规则 |
| “经过审查”“上一轮”“根据本次要求” | 删除过程，写最终事实和依据 |
| “完善”“高可用”“确保稳定” | 写已有依据的机制或指标；无依据则删除 |
| “暂时”“以后可能”“原则上” | 写真实阶段、条件和确认对象；删除未决想法 |
| “不是X而是Y”“并不意味着”等否定对照 | 改写为直接规则和条件 |
| 规范外的比较或混用提醒，如“与业务 batchId 不同，二者不可混用” | 规范已有定义时只引用规范原句；没有新增信息的提醒整句删除 |
| 重复的括注、总结、样例、模板空章节 | 保留权威定义，删除重复表述 |
| TODO、待核值、示例值、示例 URL | 在会话核实可查询的技术取值，正文写确定结果。保留影响方案成立的外部条件。示例值或示例 URL 仅在实际占位未确定时标为问题；API 示例本身必要则保留 |

项目特有的字段禁填、长度、枚举含义、数据写入范围、事务边界、失败后果和兼容性要求保留一次。与本项目接口契约无关的通用安全常识、重复提醒和包装语删除。
