# Publication Ready Docs with Jev

生成可独立阅读的交付稿。

## 范围与模板

- 按请求选择内容。设计写目标、必要改动、职责、接口、状态规则和配置；运行手册写执行条件、步骤和恢复方式；测试文档写场景、预期和实际结果。
- 参考模板时只保留适用章节，删除空章节和仅写“不涉及”的章节。用户明确要求保留全部结构时，保留结构并简短标明不适用。
- 设计默认不附部署计划、测试方案、验收矩阵、风险或证据清单。用户要求或实际改动确有需要时再写。独立审计、复盘和 ADR 保留所需分析。

## 必要设计

- 先查现有实现。可沿用的机制只说明沿用及来源。新增机制须对应明确需求或有依据的实际风险。
- 写清主体、条件、动作和结果。区分现有行为、确定的设计与已实现结果。
- 源码、配置或常规技术选择能解决的问题，由设计确定。只有缺失且影响方案成立的业务条件或外部约定，才列为待确认项并注明责任方。
- 范围外的“不执行、不涉及”说明默认删除。字段职责、真实禁止规则、兼容性限制和失败后果仍须保留。
- 保留事务边界、接口契约和必要验证。沿用且未受改动影响的流程，不增加验收。

## 表达与删除

使用短句、主动语态和固定术语，一句表达一个要点。中文借鉴 ASD-STE100 的清晰表达原则。

先判断能否删除，再润色：**删除后若不影响理解、实施或必要验证，就删除。**

- 删除讨论历史、审查过程、元话语、自我评价、假想争论和空泛承诺。无需保留的信息，不改写成另一种表达。
- 每个事实只定义一次。删除与正文或表格重复的括注、样例、速查和总结。表格某列全部相同时，改为表前一句话。
- 用项目事实替换会话指代，清除过期占位。示例、代码和参数须有来源或属于明确设计决策；不为补齐文字新增机制、指标或确认事项。

## 全文复核

核对技术语义、条件、职责、数值和不确定性。用户指出一类问题时检查全文；用户认可简洁稿后，后续修订保持该信息密度。

技术口径变更时，同步修改交付范围内的正文、表格、代码和前提条件。只维护用户指定的权威文档。

难以判断某段是否必要时，按需读取[常见坏味道](references/anti-patterns.md)或[转换示例](references/transformations.md)。

## Jev 判断

形成草稿后，使用 Jev 判断冗余表达和跨章节重复，再结合上述规则决定删、改、留。技术事实以源码、配置和用户要求为准。

在本 Skill 目录执行：

```bash
python scripts/jev_doc_review.py <input.md> --doc-type 详细设计
```

需要环境变量 `TYPESAFE_API_KEY` 和脚本所用的 Python 依赖。脚本输出 `<input>.review.md`、`<input>.review.json`，不修改原文。逐句判断、跨章节重复判断及阈值由脚本管理。

- 所有建议均按删除判断复核，包括建议保留的句子。真实约束和必要条件须保留。表格与代码不在逐句扫描范围内，另行检查。
- 用户只要求报告时交付报告；已授权修订时直接修改。除用户要求外，报告不另作长期交付物。
- Jev 调用失败时说明未完成判断，继续处理能确定的编辑，不声称 Jev 已通过。
